# ScholarFlow v0.1 设计：多智能体科研文献研究与报告生成平台

- 日期：2026-10-15（Asia/Shanghai）
- 阶段：用户已确认设计（2026-10-15）；功能待实施
- 目标用户：研究生和科研人员
- 产品目标：基于现有 GPT Researcher 底座，完成可干预、可追溯、可恢复的文献调研闭环，并以 ScholarFlow 开源发布

## 1. 需求理解与首版边界

用户希望将现有项目改造为多智能体科研文献研究与报告生成平台，并明确优先服务真实科研使用。此前提出的“文献库 → 证据阅读 → 比较矩阵 → 可追溯综述”作为首版主线。

首版采用单人、本地或受信任内网部署模式。数据保存在服务端；更换浏览器后可从同一实例恢复项目。公网多用户托管、账号权限和多人协作属于后续版本，不将无认证实例直接暴露到公网。

### 1.1 首版必须交付

1. 创建研究项目，填写研究问题、年份范围、报告语言和纳排标准。
2. 生成并编辑检索计划，人工批准后执行检索。
3. 接入现有 arXiv、Semantic Scholar、OpenAlex 检索能力，归一化论文信息并保存检索记录。
4. 导入本地带文本层的 PDF；保留没有全文的论文记录及明确来源的摘要。
5. 展示候选文献，由用户逐条或批量纳入、排除，确认本次使用的论文集合。
6. 逐篇提取研究问题、方法、研究对象或数据集、主要发现、局限，绑定原文证据。
7. 展示可编辑的文献比较矩阵，并能打开对应 PDF 版本、物理页和原文片段。
8. 生成专题综述或方法对比报告，支持基本 Markdown 编辑、保存修订和引用复核。
9. 导出 Markdown、DOCX、BibTeX；固定使用一种数字顺序引用格式。
10. 保存研究进度与阶段产物，支持刷新恢复、失败阶段重试、取消以及 worker 重启恢复。

### 1.2 后续版本

富文本协作编辑、按章节增量重写、持续订阅新论文、Zotero 双向同步、专业学科模板、扫描 PDF 的 OCR、多种引用样式、PDF/RIS 导出及公网团队部署。

首版不宣称自动完成规范化系统综述、Meta-analysis、全库穷尽检索或保证所有生成结论正确。输出报告注明数据源、检索时间、查询式、纳入集合、摘要/全文覆盖以及待核验项，帮助用户判断覆盖范围。

## 2. 现有代码与改造策略

保留 Next.js、FastAPI、LangGraph、模型适配器及现有学术检索工具。科研流程采用独立的领域层和 API，逐步替换通用网页研究界面，不在首版全局改名 Python 包或移除其他研究模式。

| 现有位置 | 核查结果 | 首版处理 |
| --- | --- | --- |
| `gpt_researcher/retrievers/arxiv/`、`semantic_scholar/`、`openalex/` | 检索器已有，但输出被压缩成 `title/href/body` | 提取共享请求及归一化能力，新增结构化学术接口，保留旧检索契约的兼容适配 |
| `gpt_researcher/retrievers/semantic_scholar/semantic_scholar.py` | 作者、年份等信息丢失；没有 OA PDF 的结果被过滤 | 科研接口保存元数据，全文可得性作为独立状态 |
| `gpt_researcher/document/`、`scraper/pymupdf/` | 加载 PDF，但后续丢失页码或合并各页文本 | 新建保留版本、物理页和片段的解析路径，共享下载安全检查 |
| `multi_agents/agents/orchestrator.py` | 已有规划、研究、审稿、发布图；无持久化 checkpointer | 新建科研图，复用适用工具和模型调用能力 |
| `multi_agents/agents/fact_checker.py` | 主要读取草稿；现有路由在达到修订上限时直接接受 | 科研核验读取引用原文；超限保留问题并转人工复核 |
| `backend/server/report_store.py` | 报告使用 JSON 文件存档 | 科研项目使用 SQLite；旧报告存储继续支持原入口 |
| `frontend/nextjs/components/ResearchBlocks/Report.tsx` | Markdown 展示及复制 | 增加报告编辑、修订及引用联动 |
| `frontend/nextjs/hooks/useWebSocket.ts` | 已有流式事件和人工反馈 | 科研流程使用持久化事件及重连补读 |
| `backend/utils.py`、`multi_agents/agents/publisher.py` | 已有报告导出 | 复用转换能力，确保导出绑定已保存的报告版本 |

建议代码边界：

```text
backend/scholarflow/
  api/            # 项目、文献、运行、证据、报告路由
  domain/         # 数据模型、状态约束、引用契约
  persistence/    # SQLite repository、迁移、文件存储
  services/       # 检索归一化、去重、PDF 解析、证据和导出
  workflows/      # 科研 LangGraph 图及各角色节点
  worker/         # 持久化任务认领、租约、重试、取消
frontend/nextjs/
  app/projects/   # 项目列表与项目工作台
  components/scholarflow/
  types/scholarflow.ts
```

领域对象不依赖 WebSocket 或 React。工作流使用 ID 引用领域对象，避免将整份 PDF 和完整项目数据库塞进图状态。

## 3. 用户流程与人工决策

### 3.1 新建项目与计划

用户输入研究问题、年份、学科提示、来源、语言及纳排标准。规划节点产生检索式、子问题和初始标准；用户可以修改。批准请求必须绑定计划 revision；未批准的计划不能启动远程检索。模型建议与用户批准分开存储。

修改已批准计划生成新 revision，供新运行使用；已开始的运行固定使用原快照。

### 3.2 检索、导入与纳入

检索结果保存来源、原始标识、查询式和获取时间。默认每个来源最多取 20 条、每次最多纳入 20 篇，均可配置。检索失败区分“无结果”和“服务不可用”，部分来源失败时展示覆盖缺口。

候选表展示标题、作者、年份、来源、出版状态、摘要、全文状态、AI 筛选建议和人工决定。AI 建议不能覆盖人工决定。

用户确认“本次纳入集合”后继续，至少包含一篇。其他未选择候选可以保留 pending，不要求先处理完所有候选。明确排除的论文保存原因；未选择不等于被排除。批量操作显示作用范围及数量。

DOI 和 arXiv 标识用于确定性匹配；标题相似仅生成合并建议。预印本与正式出版版建立关联，保留各版本，不因标题相似直接合并证据。无 DOI 的论文和用户上传的未识别 PDF 允许使用内部 ID。

### 3.3 全文、阅读与比较

优先获取可访问的开放全文，或使用用户导入的 PDF。元数据可收录与全文可获得分别判断。无法获取全文时保留论文，显示摘要依据并提供补充 PDF 的入口。

首版解析带文本层的 PDF；扫描件、损坏、加密、下载失败分别显示具体状态。缺少可用正文不触发模型编造阅读结果。

比较矩阵固定字段：研究问题、方法、研究对象或数据集、主要发现、局限。每个单元格保存原文证据，缺失项显示“未报告”。人工修改保留旧值、来源及 revision，默认变为待复核，不自动认定为正确。

### 3.4 写作、复核与导出

报告使用本次纳入集合、指定文档版本和已经提取的证据。默认结构为研究范围、主题分类、方法比较、研究分歧、局限与后续方向、参考文献，并附检索与覆盖说明。

基本编辑器支持按段修改 Markdown、插入已有引用、保存报告修订。编辑后的论断与相关引用进入待复核。矩阵发生修改时，将依赖的报告标为 outdated，原正文保留，由用户启动新一轮生成。

核验未通过时显示待处理问题。用户可以明确选择导出带问题的草稿；确认绑定 `report_version_id + verification_record_id`，不能用于后续修改或新的核验记录。此举仅确认接受草稿状态，不改变任何证据核验结果。默认导出当前已保存的指定版本；未保存编辑需要先保存。

## 4. 数据模型与不可变来源

数据库使用 UUID 内部 ID、UTC 存储时间、外键约束。UI 按用户时区显示时间。下表是领域契约，相关嵌套数据可以先保存在 JSON 字段中，数据库迁移必须有明确版本。

| 实体 | 核心字段与约束 |
| --- | --- |
| `Project` | 问题、范围、语言、当前配置及 revision |
| `PlanRevision` | 项目、不可变计划内容、检索式、标准、人工批准记录 |
| `Paper` | 逻辑论文 ID、规范化标题及关联版本；不承担项目内纳排状态 |
| `PaperVersion` | 论文、DOI/arXiv 版本标识、作者、年份、出版状态、来源记录；预印本与正式版各自保留 |
| `SourceRecord` | 数据源、外部 ID、原始元数据、查询式、获取时间及元数据来源 |
| `ProjectPaper` | 项目、论文、选定版本、AI 建议、人工决定、理由、笔记及 revision |
| `SelectionSnapshot` | 项目、不可变纳入清单、选定论文版本、人工确认记录和 revision |
| `DocumentVersion` | 论文版本、类型 `pdf/abstract`、SHA-256、文件相对路径或摘要原文、获取与解析状态；内容不可变 |
| `Passage` | 文档版本、片段正文、页码、章节、原文偏移；版本内稳定 ID |
| `ExtractionRevision` | 项目论文、输入版本、字段值及各字段证据、模型/人工来源、review 状态；保留修改历史 |
| `Claim` | 精确论断文本、所属提取项或报告段落、来源类型及核验状态；修改论断创建新 revision |
| `Evidence` | 论断 revision、片段 ID、原文引句、支持/反驳关系、定位与语义核验结果、复核记录 |
| `Run` | 项目、kind、不可变启动输入、逐阶段追加的输入/产物清单、模型及提示词配置、状态、阶段和问题列表 |
| `Job` | 运行、阶段、输入哈希、尝试、租约、产物引用、错误及用量记录 |
| `RunEvent` | 运行、递增序号、阶段、事件类型、时间和结构化数据 |
| `ReportVersion` | 运行、正文分段、论断绑定、引用映射、前一版本；保存后内容不可变 |
| `VerificationRecord` | 指定报告/论断版本、核验器版本、逐项检查、质量结论、人工复核；每次检查追加记录 |
| `CitationOccurrence` | 报告版本、段落、引用出现序号、论断 revision 与证据 ID；逐个引用位置绑定 |

报告正文、引用和书目快照不可变；后续核验、草稿确认、导出记录追加保存。outdated 是当前项目输入与报告 manifest 比较后的展示状态，quality_status 来自指定 VerificationRecord，均不改写历史正文。编辑或修正报告创建新 ReportVersion。

文档内容哈希固定物理文件；替换 PDF 创建新 DocumentVersion。旧报告仍关联旧文件，原有证据不会因为上传新版本而失效。新运行需要明确选择新版本，不能在后台替换来源。首版只允许从项目移除关联，不提供会破坏历史报告的底层文档物理删除入口。

论文原始元数据与用户修正分开保存，展示字段有可追踪的来源。外部元数据更新不能静默改写旧报告的参考文献快照。

## 5. 证据、核验和引用契约

### 5.1 定位

PDF 页码统一为从 1 开始的物理页，印刷页码可选另存。证据至少包含 `document_version_id / passage_id / page_number / quote`。摘要没有真实页码，使用字段位置及文本偏移，不能生成虚构页码。

原文匹配允许明确的空白、换行和断词规范化，同时保留原文及偏移映射；不通过删除数字、否定词或其他实质内容来制造匹配。匹配失败为 `unlocated`，不能以语义相近段落冒充精确定位。首版要求正确页码和原文摘录；坐标级 PDF 高亮可后续扩展。

### 5.2 分离三类检查

1. 书目检查：论文标识、题名、作者等是否匹配真实来源。Crossref 可作为可选的元数据补全与核对来源，缺少 DOI 本身不判为错误。
2. 定位检查：引句是否确实存在于指定版本的原文片段。
3. 支持性检查：该片段是否支持具体论断，是否遗漏条件、夸大或与其他证据冲突。

模型参与支持性检查，但模型判断不展示为确定性事实保证。记录 checker 类型、版本、理由及人工复核结果。论断状态统一为 `supported / inferred / conflicting / insufficient_evidence / needs_recheck`，证据范围另存 `fulltext / abstract`。

摘要证据只支持摘要明确写出的内容；书目和标题不能充当阅读全文的证据。研究空白与后续方向标明综合推断和检索范围，不能从“未检索到”推导“领域从未研究过”。不同研究的指标缺乏可比条件时，保留上下文，不能直接得出统一排名。

### 5.3 确定性引用生成

报告正文使用稳定引用键，例如 `[@sf_a1b2]`。一个引用键对应一个 PaperVersion 及书目快照；另用 CitationOccurrence 记录每次出现所对应的段落、论断 revision 和证据 ID。段落内论断文本保存字符范围，报告内容修改后重新建立该版本的位置绑定。同一论文在多个位置出现时分别核验，不能因一个位置通过就让其他位置自动通过。生成模型仅从本次允许的引用键中选择，未知键校验失败。程序按正文首次出现顺序生成数字编号和参考文献。

引用映射必须存在，文档版本须可用，证据须指向确切论断。新增或修改带引用段落后，仅相关绑定转为 needs_recheck；没有依据的新增事实保留为待核验。用户输入外部链接或手写参考文献不等于自动建立已核验绑定。

未知引用键、版本归属错误等结构错误阻止正式导出；允许导出带问题草稿时也不能伪造有效引用。语义未通过或证据不足的项可以在确认指定版本后随草稿导出，并在正文标记及问题附录中保留。

Markdown、DOCX 和 BibTeX 使用同一 ReportVersion 的映射。BibTeX 只输出该报告实际引用的论文，缺失元数据保留缺失状态，不由模型补造。导出失败可独立重试，不重新运行文献阅读和写作。

## 6. 多智能体工作流

六类角色各有输入与结构化输出，可以共享模型适配器和底层工具：

| 角色 | 输入 | 输出 |
| --- | --- | --- |
| Planner | 项目问题和范围 | PlanRevision 草稿 |
| Retriever | 已批准计划 | 查询记录、SourceRecord 和候选版本 |
| Screener | 候选摘要和纳排标准 | AI 建议及理由，保留人工决定 |
| Reader | 纳入论文、指定文档片段、字段模板 | 提取项、Claim 和 Evidence 候选 |
| SynthesizerWriter | 已纳入的提取项、证据及允许引用键 | 分类比较和结构化报告草稿 |
| Verifier | 论断、绑定原文、引用映射 | 定位和支持性核验、待处理问题 |

去重、下载、文件哈希、文本匹配、引用编号、预算检查和格式转换由确定性服务完成。论文正文、来源元数据和模型输出均作为不可信数据处理，不能执行其中的指令、命令或任意路径。

科研图按“计划 → 人工批准 → 检索与建议 → 人工确认纳入 → 文档准备 → 并行逐篇提取 → 综合写作 → 核验 → 保存报告”运行。首版逐篇并发默认为 2。Verifier 发现可修正问题时最多自动改写一次，仍有问题进入 needs_review；预算耗尽也不能自动核验通过。

主 Run.kind 为 `literature_review`，可从 plan、search 或 analyze 阶段进入。plan 入口只需项目问题；search 入口须带已批准 PlanRevision；analyze 入口须带已批准计划和 SelectionSnapshot。全流程在等待计划批准和确认纳入时进入 waiting_for_user，动作必须指向对应对象及 expected_revision。后续 `import / report_check / export` 为独立辅助运行，不重新打开已完成的研究运行。

Run 的启动配置一次固定；流程中新产生的数据以追加、写入后不可变的阶段 manifest 保存。批准计划时固定检索输入，确认纳入时固定 SelectionSnapshot，文档准备完成后固定每篇所用 DocumentVersion，提取完成后固定 ExtractionRevision 清单，再交给写作。重试读取这些固定版本，不能重新读取项目“当前版本”。用户在人工等待阶段批准的是尚未固定的下一阶段输入；修改已固定的输入须创建新 Run。

## 7. 持久化任务与恢复

SQLite 保存领域数据、任务、事件及科研图检查点，API 与独立 worker 访问同一实例数据目录。首版一个 worker 进程，内部限制并发；远程请求、LLM 调用、PDF 解析不占用长数据库事务。

Run 状态：`queued / running / waiting_for_user / needs_review / completed / failed / cancelled`。`stage` 单独表示计划、检索、筛选、解析、提取、写作、核验或导出。`quality_status` 单独表示未核验、通过或存在问题；执行完成不代表核验通过。

Job 状态：`queued / running / succeeded / failed / cancelled`。人工审批及待复核由 Run 管理，问题产物可保存为成功的阶段结果，同时将 Run 转为 needs_review。批准指定版本的草稿可使主 Run 进入 completed，但该核验记录的 quality_status 仍为存在问题，确认不覆盖后续报告版本。

合法恢复动作：waiting_for_user 仅在对应批准或确认成功后继续；needs_review 在问题修正并复核后继续，或明确接受指定草稿；failed 仅重试原输入的失败阶段；completed/cancelled 不直接继续，修改输入后创建新运行。取消请求对尚未终结的 Run 生效；辅助复核及导出运行固定引用目标报告版本。

关键契约：

- Job 带 `lease_owner / lease_expires_at / attempt_no`，worker 续租；租约过期的未完成任务可被重新认领。
- 认领任务、提交产物及状态变更使用短事务；提交检查当前租约与 attempt，阻止过期 worker 覆盖新结果。
- 幂等键包含任务类型、输入版本哈希和相关配置版本；重复提交同一操作返回已有任务。明确重新运行产生新的操作 revision。
- 已成功且输入版本相同的解析和提取产物可以复用；失败只重试该阶段。新文档需重做相关提取，首版允许重新生成整份报告，局部章节增量更新留到后续版本。
- 图检查点与阶段产物均持久化。恢复时以成功产物为准，节点先检查幂等产物，避免仅依赖内存图状态。
- 进程崩溃可能发生在外部调用完成、结果尚未落库之间，因此外部调用按至少一次执行设计，可能重复调用并计费；记录各 attempt、请求哈希、provider 请求 ID（若有）及用量，不承诺 exactly-once 计费。
- 取消阻止后续阶段及新的远程调用；已发出的调用可能仍产生费用，回来的结果不再发布为取消运行的正式报告。
- 网络错误有限次退避重试；解析永久错误、核验失败、预算不足保存原因和中间产物。用户可补全文、减少范围或调整配置后创建后续运行。
- 默认单次运行最多发起 100 次模型调用，可配置。预估费用与实际记录分开显示；缺少价格配置时显示 token/调用用量，不编造金额。
- 事件先落库再通知。客户端按序号补读，丢失 WebSocket 连接不影响任务继续。

## 8. API 边界

所有下列路径以 `/api/v1` 为前缀。旧 `/api/reports`、`/report/`、`/ws` 保留原契约；新工作台不借助旧聊天接口启动研究。

| 路由 | 行为 |
| --- | --- |
| `GET/POST /projects`，`GET/PATCH /projects/{id}` | 项目列表、创建、读取及修改 |
| `GET/POST /projects/{id}/plans` | 计划历史、创建修订；模型规划由异步运行执行 |
| `POST /projects/{id}/plans/{revision}/approve` | 批准明确版本 |
| `GET /projects/{id}/papers` | 候选、纳入状态和检索覆盖 |
| `POST /projects/{id}/imports` | 上传 PDF、导入外部标识或已选检索记录；返回异步导入 ID |
| `PATCH /projects/{id}/papers/{paper_id}` | 选择论文版本、纳排决定、理由和笔记 |
| `POST /projects/{id}/selections` | 冻结本次纳入集合及 revision |
| `GET /papers/{paper_id}/versions` | 论文版本及元数据来源 |
| `GET /documents/{id}`，`GET /documents/{id}/file` | 文档解析状态及受控文件读取 |
| `GET /documents/{id}/passages` | 版本固定的原文片段和页码 |
| `POST/GET /projects/{id}/runs` | 创建或列出运行，指定 kind、入口阶段及该阶段要求的输入版本 |
| `GET /runs/{id}`，`GET /runs/{id}/jobs` | 状态、阶段、问题、任务及用量 |
| `POST /runs/{id}/actions` | 继续、取消、重试失败阶段或明确接受问题草稿 |
| `GET /runs/{id}/events?after={seq}` | 持久化事件补读；WebSocket 按相同序号通知 |
| `GET/PATCH /projects/{id}/extractions/{paper_id}` | 比较矩阵和提取项修订 |
| `GET /claims/{id}/evidence`，`POST /evidence/{id}/reviews` | 原文回链和人工复核 |
| `GET/POST /projects/{id}/reports` | 报告列表或保存编辑版本，生成工作由 runs 启动 |
| `GET /reports/{version_id}` | 指定版本正文、引用、质量状态及过期原因 |
| `POST /reports/{version_id}/checks` | 对指定版本异步复核 |
| `POST/GET /reports/{version_id}/exports` | 发起导出或查询导出结果 |

异步操作返回 `202` 与稳定的操作、运行或任务 ID。启动、导入、重试和导出支持 `Idempotency-Key`。修改和审批带 `expected_revision`，冲突返回 `409`，前端保留未保存内容，不静默覆盖。错误包含稳定错误码、可读原因和是否可重试。

运行服务校验批准计划、冻结纳入集合和版本归属；不能通过直接调用接口绕过人工阶段。服务端逐次校验项目资源归属、上传限制和下载地址；复用现有 URL 安全检查，文件路径由存储层生成。

前置条件按阶段校验：plan 不要求已有批准计划或纳入集合；search 要求已批准计划；analyze 要求冻结纳入集合。服务端拒绝不合法的状态动作，返回 409 与当前阶段及待处理对象。科研事件 WebSocket 为 `/api/v1/runs/{id}/ws?after={seq}`，HTTP 补读和 WebSocket 使用相同事件序号。

## 9. 页面与客户端状态

项目列表显示最近项目、当前阶段、待处理事项及继续入口。项目工作台提供“计划、文献、证据/矩阵、报告”四个工作区，运行记录作为可展开面板。

- 计划：范围、检索式和标准编辑，批准与修改记录。
- 文献：可筛选表格、AI 建议、人工纳排、导入、全文状态、确认本次纳入。
- 证据/矩阵：选择论文后联动 PDF、原文摘录和结构化字段；未定位、仅摘要、人工修改均有文字状态。
- 报告：桌面为大纲、正文、证据三栏；提供编辑/预览、保存、核验问题、导出版本选择。
- 运行面板：阶段计数、失败原因、重试、取消、用量和事件；不显示没有测量依据的精确剩余时间。

手机采用标签切换而不是强制三栏，使用相同 API、Run ID 和状态。首版允许基本 Markdown 编辑，不要求移动端富文本操作。刷新从服务端重新读取项目与任务，再按事件序号补读；localStorage 仅用于临时未保存草稿和界面偏好。

## 10. 验收与验证策略

首版交付按以下行为验收，测试使用固定元数据及可分发的自建文本 PDF，默认不依赖付费服务或实时网络。

| 场景 | 必须观察到的行为 |
| --- | --- |
| 计划批准 | 未批准检索计划时远程检索不会执行；批准与 Run 绑定准确 revision |
| 论文纳排 | AI 建议不改变人工决定；排除论文不进入本次分析；确认选中论文后，其他 pending 候选不阻塞 |
| 元数据与版本 | 同一 DOI 的多来源记录可归一化；预印本与出版版保留关联及各自来源；无 DOI 也可导入 |
| 摘要边界 | 无全文论文保留；摘要证据标明范围；不存在于摘要的实验数字不被标为 supported |
| PDF 证据 | 点击矩阵和报告引用打开准确文件哈希、物理页及原文；引句不匹配显示未定位 |
| 冲突与超限 | 人为注入错误数字或反向结论时保留冲突；修订或预算上限不能自动变成核验通过 |
| 人工编辑 | 修改矩阵或报告保留历史；关联报告过期或引用待复核；不覆盖人工内容 |
| 恢复与幂等 | 六篇提取完成后终止 worker，恢复复用已落库结果；相同请求不创建重复逻辑记录；租约过期结果不能覆盖新尝试 |
| 历史来源 | 替换 PDF 后旧报告仍打开旧文档；新运行使用新版本并重新提取相关数据 |
| 导出 | 三种格式绑定同一已保存报告；编号、书目、引用集合一致；带问题草稿有明确标识 |
| 跨客户端 | 电脑启动后手机打开同一实例项目，纳排决定、进度和已保存报告一致 |
| 兼容性 | 原研究入口和旧检索返回契约继续可用，不因新增领域字段破坏现有调用 |

实施时重点增加领域约束、provider 归一化、PDF 定位、任务恢复、引用与导出集成验证，以及一个浏览器完整流程验证。涉及旧模块时运行对应现有测试，不为纯展示文案或实现细节增加镜像测试。

人工质量评估使用三个研究主题，逐项检查论文身份匹配、字段提取、证据定位、论断支持以及检索覆盖。元数据正确和语义支持分开报告，不用链接域名相同代替引用正确。

## 11. 开源交付与发布准备

保留 GPT Researcher 上游来源说明与历史，不将现有功能描述为全部原创。当前 `LICENSE` 为 Apache 2.0，而 `pyproject.toml`、`setup.py` 包元数据声明 MIT；发布前核对目标上游版本与相关说明，统一准确的项目许可声明。

首版交付包括中英文 README、架构说明、可复现示例项目、自建 PDF 示例、无密钥演示数据、`.env.example`、Docker Compose 的 API/worker/前端启动方式、持久化目录说明和贡献指南。

模型及检索密钥仅由服务端读取，不发送到客户端或写入研究导出。模型与数据源配置显示必要条件；连接失败有可操作错误。上线前检查待公开文件和 Git 历史中的凭据、个人文件及论文分发权限，样例不直接打包不可分发的全文。

GitHub 发布目标已由用户创建，为 `https://github.com/yibenwulong/ScholarFlow`。该仓库配置为 origin，上游 GPT Researcher 保留为 upstream；默认推送目标为 origin，不向上游 remote 推送场景改造。

## 12. 实施拆分与设计自检

后续实施计划按依赖顺序拆分：

1. 领域模型、SQLite 迁移和项目/文献最小 API。
2. 学术元数据适配、纳入集合和版本保留。
3. PDF/摘要解析、证据定位及比较矩阵。
4. 持久化 worker、科研图和人工阶段。
5. 写作、核验、报告编辑与导出。
6. 前端完整流程、回归验证、示例和开源文档。

各步骤交付可检查产物，先完成一篇论文的纵向流程，再扩展并发检索与批量分析。此顺序是设计拆分，不替代带具体文件及验证命令的实施计划。

自检关注：人工建议与决定是否分离；旧文档能否保持追溯；执行状态是否与质量状态分离；异常是否保留产物；引用是否绑定论断版本；API 与手机/桌面流程是否一致；首版是否混入后续协作与高级编辑范围。
